## Input and authorization

```js
import { createDeliveryTrendsInput, calculateDeliveryTrends }
  from './js/delivery-trends-adapter.mjs';
const input = createDeliveryTrendsInput({
  source: 'production', // exactly production | uat | synthetic; caller must establish truth
  asOf: '2026-10-14T00:00:00Z', // caller-supplied observation time; never generated by engine
  anchorWeekId: '2026-W41', windowWeeks: 6, // 6 or 12
  publicationMode: 'released', // released | include-drafts; authorized caller chooses
  scope: { projectLevel: 'system', projectKeys: null },
  canReadWeek: week => /* existing week access policy */ false,
  canReadProject: (project, week) => /* existing project access policy */ false,
  weeks: [{
    weekId: '2026-W41', // adapter also accepts __documentId; never derives from label
    reportingPeriod: { year: 2026, week: 41 }, // validated ISO week-year, ISO week number
    isReleased: true, version: 1,
    projects: [{ projectId: 'stable-id', code: 'SYS-1', name: 'Authorized name',
      projectManager: 'Authorized display name', progress: 30, projectLevel: 'system',
      visibility: 'active', lifecycle: 'active', status: 'green', baselineId: 'baseline-1' }]
  }]
});
const result = calculateDeliveryTrends(input);
```

The predicates must return boolean true to include data. Errors abort with a generic message;
rejected week/project details are never returned. Do not pass the engine unfiltered Firestore
snapshots. The engine has no access-granting logic: direct callers are responsible for prior
permission checks, and source/asOf authenticity cannot be independently verified by a pure module.
Predicates mirror existing permissions; they do not broaden them. Scope filtering is performed
inside the engine so entered/exited scope can be distinguished from missing observations.
Project owner/PM display metadata is retained only after authorization; other fields such as
budgets, arbitrary email fields and unrelated records are not forwarded by the adapter.

Actual legacy records need authoritative ISO periods supplied by the data-owning layer. No
weekLabel guessing, schema writes or migration are included. A missing period makes the result
unavailable. Source is never defaulted to Production. Unsupported policies/windows/scopes,
malformed weeks and duplicate IDs/periods fail closed with generic warnings.

## Definitions

- Percentage: finite number or a trimmed decimal digit string, 0..100 inclusive. Missing,
  blank, booleans, hexadecimal/exponent strings, invalid objects and out-of-range values are null.
- Current completion: mean of valid in-scope observations; denominator `validProgressCount`
  differs from `scopeProjectCount` when observations are missing. It is supporting information.
- Comparable set: same unique identity, present and in scope in both consecutive ISO weeks,
  both percentages valid, no confirmed rebaseline boundary.
- Weekly Progress Gain: signed mean of current-minus-previous progress over that set, in pp.
- Projects Progressed: count of strictly positive differences over the identical set.
- When denominator is zero, both metrics are null and comparableCount is zero.
- Two decimals are returned for calculated numbers; display formatting remains presentation-owned.
- RAG counts use green/yellow/red; all other values are unknown. RAG does not prove lifecycle.
- ID matching is preferred. Code-only identity uses trimmed case-insensitive code and is explicitly
  legacy-provisional. ID/code mixed history is not joined, and code-only renames are not inferred.
- A duplicate matching key anywhere in the requested source window excludes that key throughout
  the window. Names/indexes are never identity. Case changes cannot hide legacy duplicate codes.
- `confirmedCompleted` requires active/on-hold → completed on a matched consecutive observation.
  Missing lifecycle is unknown; first observed completed is not a completion transition.
- Disappearing is `missingObservation`, never completed. Scope exit with an existing observation
  is `exitedScope`; entering an existing identity is `enteredScope`, not newly created.
- `firstObserved` means first seen in the supplied requested history, not a creation date.
- Confirmed reset requires current `rebaseline: {verified:true, fromBaselineId, toBaselineId}`
  matching the two nonempty, different baseline IDs. Caller must establish the evidence's truth.
  Unverified reset claims/declines retain their signed difference and receive baseline warnings.
- Baseline IDs absent or changed without confirmed reset yield `baselineVerification: unverified`;
  unchanged IDs yield consistent, not proof that historical records are immutable.

## History/output

Top-level fields retain `delivery-trends/v1`, provenance, status, summary, weeklySeries, projects,
changes and warnings. Status is ok/partial/unavailable; partial may contain usable numbers with
explicit limitations. Warnings are sanitized `{code,message,weekId,count}` objects.

N displayed weeks are N consecutive calendar slots ending at the anchor; N+1 authorized source
weeks are needed to calculate every displayed difference. Missing calendar slots remain present,
with null weekId/gain/completion. Released filtering occurs before window selection. No comparison
substitutes a non-consecutive week; withdrawn/draft records under released policy become gaps.
Past values may change when the caller supplies revised historical data; result is tied to asOf.

`weeklySeries[]` includes reportingPeriod, label, gainPp, comparableCount, projectsProgressedCount,
currentCompletionPct, scopeProjectCount, validProgressCount, missingProgressCount, health, changes
and comparison diagnostics. `weeklyProgressGainPp` is retained as an exact alias of gainPp.

`projects[]` includes key, projectId, code, name, projectManager, status, identityConfidence,
currentCompletionPct, weeklyChangePp, comparable, trend and diagnostic history. The project union
covers the displayed scope history: no longer observed/out-of-scope projects have null current
metrics and comparable false. `trend[]` has weekId/label/progressPct; diagnostic `history[]` retains
period/completionPct/observation. Gaps are not filled, interpolated or treated as zero.

Top-level changes are anchor-week changes, except ambiguousIdentity lists unresolved matching
identities in the requested history using generic labels only. Array length counts unresolved
identity groups (or unidentified records), not confirmed real-world projects.
Per-week lifecycle/scope changes appear in weeklySeries; ambiguity is global, with week-specific warnings. Changes reference only authorized identity/display
metadata; ambiguous records' raw details are withheld. confirmedRebaseline is an additive diagnostic
category, not a replacement of any approved public field.

## Packaging and future wiring (no renderer edits in this PR)

- Browser static import of `js/delivery-trends-adapter.mjs` pulls in `shared/delivery-trends.mjs`.
  Existing Hosting collector follows this dependency; there is no product wiring yet.
- `node scripts/package-delivery-trends.mjs` generates the byte-identical tracked PDF source and
  SHA256 in `pdf-service/src/generated/`. Never edit the generated module by hand.
- `node scripts/package-delivery-trends.mjs --check` rejects copy/hash drift without repairing it;
  CI explicitly runs the check. Regenerate and commit whenever authoritative source changes.
- PDF code can import `./generated/delivery-trends.mjs`. Docker verifies checksum and import after
  copying src; the supported deployment script additionally verifies against repository canonical
  source before invoking deployment. Existing security gates/target identities remain unchanged.
- Future PDF data adapter must provide the same authorization, publication, scope, anchor, ISO
  periods, raw values and N+1 history. Current 6-record backend caps cannot meet the new contract.
- Do not register a new PDF section or wire navigation until the Control Plane authorizes integration.
- This phase does not validate real Production history or deploy anything.
