# Company Copilot Packed Weekly Summary Repair Design

**Date:** 2026-08-17  
**Status:** Approved design; implementation planning pending review

## Purpose

Make a Weekly Summary generated by the company-managed Copilot usable with one paste and one Save action, even when Copilot places structural labels on the same physical line. The browser must convert only a complete, unambiguous labelled structure into the existing canonical Weekly Summary grammar. The stored canonical summary and the resulting Overview PDF must remain complete, structurally valid, and visually stable.

This design does not require company Copilot text to leave the company environment. It also does not require a user to retry a different AI model after a formatting-only failure.

## Evidence and root cause

The company Copilot screenshots show labelled content in this shape:

```text
WEEKLY MOVEMENT Portfolio Summary: <portfolio text>
- Project: <project name> Movement: <movement text> Blocker: <blocker text> Next step: <next-step text>
MANAGEMENT ASK
- Project: <project name> Decision / Support needed: <decision text> Business impact: <impact text>
```

The current normalizer only normalizes individual lines. It can add a missing project marker or normalize punctuation, but it deliberately does not split multiple semantic labels found on one line. Consequently, the validator interprets the text after `Project:` as part of the project name, cannot match the project, and then reports missing field labels. The failure is browser-side validation before any Firestore write or PDF request.

## Goals

- Automatically repair the observed company Copilot packed-label format when every required label is present once and in the required order.
- Preserve the existing canonical stored form, current-versus-historical project membership rules, correction dialog, save behaviour, and PDF defensive validation.
- Test a minimum 100-case no-sensitive-data corpus without requiring 100 manual AI generations.
- Verify every accepted corpus case against the PDF structural contract and verify representative generated PDFs for content preservation and pagination stability.
- Keep all company Copilot text on the company computer. No dashboard telemetry, repository fixture, console log, or API call may contain copied company AI output.

## Non-goals

- Calling GPT-5.6, GPT-5.5, Sonnet, Opus, Gemini, or Copilot through an API.
- Choosing a preferred AI model or asking a user to switch models after a format-only failure.
- Inventing a missing movement, blocker, next step, decision, business impact, or project identity.
- Accepting unlabelled prose, tables, Markdown headings, duplicate labels, or out-of-order labels.
- Migrating historical persisted summaries.
- Sending Weekly Summary content to a new service or storing diagnostic telemetry.

## Design

### 1. Add a safe packed-label expansion stage

`normalizeWeeklySummaryForSave` will retain its current line-level normalization and add a pure packed-label expansion stage before canonical validation. The stage receives only the pasted source string and returns expanded text plus correction records. It has no Firestore, DOM, PDF, analytics, or network dependency.

The expansion stage recognizes these exact, case-insensitive labels, with ASCII or full-width colons:

- `WEEKLY MOVEMENT`
- `Portfolio Summary:`
- `Project:`
- `Movement:`
- `Blocker:`
- `Next step:`
- `MANAGEMENT ASK`
- `Decision / Support needed:`
- `Business impact:`

It will make these structural changes only when the labelled sequence is complete and ordered:

1. Split `WEEKLY MOVEMENT` from a following non-empty `Portfolio Summary:` on the same line.
2. Split one movement entry into four lines when a `Project:` line contains exactly one ordered sequence of `Movement:`, `Blocker:`, and `Next step:`.
3. Split one Management Ask entry into three lines when a `Project:` line contains exactly one ordered sequence of `Decision / Support needed:` and `Business impact:`.
4. Retain the existing normalization of list markers, indentation, label capitalization, whitespace, CRLF, and full-width punctuation after expansion.

For a successful expansion, the output is exactly the existing canonical grammar:

```text
WEEKLY MOVEMENT
Portfolio Summary: <portfolio text>
- Project: <official project name>
  Movement: <movement text>
  Blocker: <blocker text or None>
  Next step: <next-step text>
MANAGEMENT ASK
- Project: <official current project name>
  Decision / Support needed: <decision text>
  Business impact: <impact text>
```

The parser must treat labels as separators, not as content to rewrite. It captures the text between adjacent labels verbatim after trimming surrounding whitespace. It never generates text that was absent from the input.

### 2. Fail closed for ambiguous or incomplete packed text

Expansion is not attempted, and the existing red validation panel remains blocking, when any of these conditions applies:

- a required label is absent, repeated, or appears out of order;
- the text segment for a required label is empty;
- one line mixes movement and Management Ask field families;
- a line contains a Markdown heading, table, code fence, or unlabelled prose;
- the project reference cannot resolve to the permitted current or comparison-week population; or
- a removed/historical project is used in `MANAGEMENT ASK`.

This rule makes the repair deterministic. A complete packed label sequence is reflowed; an incomplete or ambiguous narrative remains visible to the user and cannot be saved. A red validation state therefore means the system lacked enough verified structure, not that the user should change AI models.

### 3. Preserve membership and user-visible feedback

After expansion, the existing contextual membership rules continue unchanged:

- `WEEKLY MOVEMENT` accepts current active projects and prior-week projects that were removed this week.
- `MANAGEMENT ASK` accepts current active projects only.
- The canonical source uses the official dashboard project display name.

When expansion and validation succeed, the app saves once and shows the existing yellow `Summary corrected` dialog. The dialog will include structural correction messages such as:

```text
Line 1: split WEEKLY MOVEMENT and Portfolio Summary into separate lines.
Line 4: expanded a packed movement entry into Project, Movement, Blocker, and Next step fields.
```

The dialog is local browser UI. It does not transmit, persist, or log the pre-correction content. When expansion is unsafe, the existing red panel names the missing or invalid structural element and the dialog remains open with the source unchanged.

### 4. Keep browser and PDF contracts aligned

Browser save validation is the contextual identity boundary. It stores only canonical text after contextual project resolution. The PDF service remains a defensive structural boundary and must continue to reject a malformed persisted summary with HTTP 422 before rendering an Executive Summary page.

The browser and PDF services may keep separate module files because the PDF service executes server-side, but both are exercised by the same corpus. For every accepted browser result, the test will pass its canonical text to `validateWeeklySummaryForPdf`. The test will require PDF validation success and an idempotent second browser normalization with zero corrections.

PDF stability has two levels:

1. **Contract stability for every accepted corpus case.** Every accepted canonical summary must be parseable by the PDF contract and eligible for report-data loading.
2. **Rendered-layout stability for representative cases.** A selected set representing each structural family, the longest field values, six movement entries, four Management Ask entries, and a removed-project movement must render through the real PDF test path. The test must confirm a non-empty PDF, all expected project and field text in extracted PDF content, no missing Executive Summary page, no blank continuation page, and no element exceeding the printable-page height.

The existing serialized browser/PDF test runner remains the required entry point for rendered PDF checks so concurrent Chrome launches cannot produce intermittent failures.

## 100-case privacy-preserving corpus

The corpus will contain 20 synthetic `week contexts`. A context contains only fictional project names and a membership relationship; it contains no real reporting text, customer data, Copilot output, Firestore export, or company identifier. The 20 contexts collectively cover:

- one to six current active projects;
- zero to four Management Ask entries;
- one removed/released comparison-week project;
- added, stable, and removed portfolio states;
- names containing spaces, slashes, punctuation, and case/whitespace variants;
- long but valid field values; and
- the maximum supported project and ask counts.

Each context runs five format families, for exactly 100 fixed cases:

| Family | Cases | Expected result |
|---|---:|---|
| Canonical multiline form | 20 | Accept with zero corrections |
| Marker, indentation, colon, and CRLF variants | 20 | Accept and normalize harmless presentation differences |
| Company Copilot packed movement entries | 20 | Accept, expand labelled movement fields, and show corrections |
| Packed headings and packed Management Ask entries | 20 | Accept, expand complete labelled structures, and show corrections |
| Safety negatives | 20 | Reject with a precise error and no canonical text |

Safety-negative cases rotate missing labels, duplicate labels, reversed labels, empty values, mixed field families, unknown projects, historical management asks, Markdown/table input, and excessive asks. They must remain rejected after all repair changes.

Beyond the 100 fixed cases, a deterministic mutation generator will create additional local variations of whitespace, line endings, list markers, colon style, packed-line boundaries, and long values. These generated cases are supplementary regression coverage; they do not replace the named 100-case release gate.

## Company environment verification without content export

The company-controlled Copilot models—GPT-5.6, GPT-5.5, Sonnet, and Opus—are treated as input sources, not fallback models. The implementation will not call them or export their output.

The one optional company-side black-box confirmation after deployment is to paste a newly generated summary into the dashboard and observe the local result. The user may retain only a screenshot and one of these non-sensitive outcomes:

- `saved without correction`;
- `saved with packed-format correction`; or
- `blocked with a structural error`.

No twenty-run manual matrix is a release requirement. A new screenshot that exposes a new format shape can be translated into an anonymous structural fixture using fictional names and placeholder facts; the original company text never enters the repository.

## File and component boundaries

- `js/weekly-summary-contract.mjs`: pure browser normalization, packed-label expansion, canonical validation, correction records, and contextual membership checks.
- `pdf-service/src/weekly-summary-contract.js`: structural validation of canonical saved summaries only; no contextual membership lookup.
- `tests/weekly-summary-corpus.mjs`: named 100-case synthetic corpus and deterministic mutation seeds.
- `tests/weekly-summary-corpus.test.mjs`: browser normalization, idempotence, expected corrections/errors, PDF-contract parity, and corpus-count assertions.
- `tests/weekly-summary-normalization.test.mjs`: focused packed-line expansion unit tests.
- `tests/weekly-summary-correction-ui.test.mjs`: correction-dialog structural messages and non-blocking save UI assertions.
- `pdf-service/test/executive-summary-brief.test.mjs` and `pdf-service/test/report-data.test.mjs`: invalid-persisted-summary guard and canonical packed-repair output acceptance.
- Existing PDF layout tests: representative rendered PDF content, continuation, page-height, and non-empty-output assertions.

## Acceptance criteria

- The named corpus has exactly 100 unique cases: 80 accepted and 20 rejected.
- All 80 accepted cases normalize to canonical text, pass second-pass idempotence, and pass the PDF structural validator.
- All 20 negative cases fail with a specific expected diagnostic and produce no canonical text.
- The observed company Copilot packed-line shape is represented by synthetic fixtures using fictional data and is accepted after expansion.
- Existing Gemini marker and punctuation variants remain accepted.
- A packed entry lacking any required label, containing a duplicate/reversed label, or referring to an unknown project remains blocked; no fact is invented.
- Root dashboard and `team-2` use the same browser contract and expose equivalent correction feedback.
- Representative real PDF renders preserve every expected Executive Summary field and project name, contain at least one PDF page, contain no blank Executive Summary continuation page, and satisfy existing page-height assertions.
- Full browser, corpus, PDF-contract, report-data, and rendered-layout test suites pass.
- The implementation adds no Copilot/Gemini API, telemetry, raw company text fixture, Firebase schema change, or new deployed service.

## Coverage interpretation

Passing all 100 fixed cases means 100% coverage of this defined structural input contract, not a claim that arbitrary future AI prose is always repairable. It specifically guarantees that the known company packed-label format and all named safe variations are handled without switching models.

The 100-case gate is a deterministic product-quality measure. Any future unknown format is added only as an anonymous structural fixture after it is observed; it must be represented without retaining company text.
