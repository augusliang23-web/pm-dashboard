# Weekly Summary AI Normalization Design

## Purpose

Make a Weekly Summary generated by Copilot or Gemini usable through one paste and one save. The dashboard must normalize harmless AI formatting variation itself while retaining a strict, PDF-safe canonical summary.

This replaces the current experience in which a missing list marker such as `-` blocks an otherwise labelled summary.

## Root cause

The current browser contract accepts only `- Project:` while AI clipboard output can arrive as `Project:`, `* Project:`, or `• Project:`. Separately, the comparison prompt supplies a union of current and prior active projects, including projects removed this week, while save validation permits only current active names. The prompt and validator therefore disagree about valid content.

## Design

### 1. Normalize before validating

The browser will call one summary parser that returns:

- canonical text ready to store;
- recognized movement and management-ask project references;
- non-blocking normalization notes; and
- blocking semantic errors, if any.

The parser accepts the following equivalent project-entry prefixes and writes each as `- Project:`:

- `Project:` with no marker;
- `- Project:`;
- `* Project:`; and
- `• Project:`.

It will also normalize CRLF line endings, leading indentation, label capitalization, and ASCII/full-width colon spacing for the required labels. It does not rewrite sentences, invent a missing field value, silently discard a project entry, or change the management no-decision sentence.

When only normalizations were needed, saving proceeds automatically. The success toast reports that the summary was normalized and saved. The textarea is updated to the canonical result after the successful write.

### 2. Resolve project references from the comparison population

At save time, the permitted movement-project population is the union of:

- current-week active projects; and
- prior-week active projects that are absent from the current active list (removed/released this week).

The parser maps a recognized name to its official display name, using exact match first and a case/whitespace-normalized match second. The canonical output always uses the official name.

Removed/released projects are valid `WEEKLY MOVEMENT` entries because their removal is meaningful week-over-week movement. Only current-week active projects are valid `MANAGEMENT ASK` entries.

An unresolvable project identity remains a blocking error. This is the one case where the system cannot safely invent a mapping or publish an unverified project statement. It will name the unmatched value and distinguish it from repairable formatting.

### 3. Generate a compatible AI prompt

The copied prompt will contain two explicit lists:

- `CURRENT ACTIVE PROJECTS` — permitted for movement and management-ask Project entries; and
- `REMOVED SINCE LAST WEEK` — may be used only as a movement entry, never as a management ask.

It will ask for one entry per meaningful supplied movement rather than an unconditional four-to-six entries. This removes the conflict when a portfolio has only one active project.

The prompt will continue to show the canonical example, but will no longer threaten rejection for harmless presentation differences. The dashboard, rather than the model, owns canonical formatting.

### 4. Preserve the PDF safety boundary

PDF export receives only canonical summaries written by the browser. Its guard uses the same structural parser/normalizer rules and rejects missing headings, incomplete required fields, unsupported Markdown/table content, and invalid management-ask shapes with HTTP 422.

The PDF service validates the saved structural contract without requiring a current-only project-name lookup, because a valid weekly movement may refer to a project removed during the comparison period. Browser save validation remains the contextual identity boundary.

## User-visible flow

1. User copies Gemini or Copilot output and pastes it into Weekly Summary.
2. User selects Save Weekly Summary once.
3. The app canonicalizes benign punctuation/list-marker/spacing differences and resolves known current or recently removed projects.
4. The app saves and reports any normalizations.
5. The saved canonical source is used by Overview and PDF export.

Only an AI reference that cannot be matched to either week, or prose that lacks a required field value, stops the save with a specific message.

## Test coverage

Tests will be written before implementation for:

- Gemini-style `Project:` entries with no leading marker becoming canonical and saving;
- `*` and `•` project markers becoming canonical;
- a known prior-week released project being accepted for Weekly Movement;
- a released project being rejected only when used in Management Ask;
- exact/case-whitespace canonical project-name resolution;
- unknown project identity remaining a blocking error;
- prompt sections for current active and removed projects; and
- PDF structural acceptance of a canonical summary that includes a released movement project.

Both root and `team-2` entry points must have identical behavior.
